## 2. What this measures that the published figures do not

Our runtime, `cql-execution` 3.3.x, already has a public report card at `cql-tests-runner.quality.hl7.org`
— **1,533 pass / 81 fail / 113 skip / 4 error**. **That run used the Java translator.** We translate with
the JavaScript one, `@cqframework/cql` 4.0.0-beta.1, and that delta has not been published anywhere.

**The comparison is indicative, not like-for-like, and must be quoted that way.** The published run used
an earlier, smaller corpus (~1,731 cases against our 1,835) and skipped 113 cases we grade. What *is*
directly comparable: **our 4 runtime errors and their 4 errors are the same four cases** — `minimum Long`,
`maximum Long`, `1 * 1L`, `Precision(1.58700)`.

## 4. Findings

### F1 — The JS translator does not implement `Slice` (10 of the 12 translation errors)

`Slice({1,2,3,4,5}, 1, 3)` and every other arity: `Could not resolve call to operator Slice with
signature (list<System.Integer>, System.Integer, System.Integer)`. The operator is in the CQL
specification and the corpus tests it; our translator has no overload for it. The remaining two are
`timezone from …` (`Timezone keyword is only valid in 1.3 or lower`) and `ToConcept(Code)`
(`Expected an expression of type 'List of System.Code'`).

**Impact on WorkWell: none today** — no measure we run uses `Slice`, `timezone from`, or `ToConcept` on a
single `Code`. Reported because it is exactly the unpublished JS-vs-Java delta.

### F2 — The JS translator ACCEPTS 36 expressions the corpus marks invalid

Only 6 of the 42 `invalid` cases are refused. The accepted ones include integer literals outside the
Integer range (`Ceiling(2147483648)`), overflow (`Exp(1000)`), domain errors (`Ln(0)`) and
`minimum Boolean` / `maximum Boolean`.

**This is the finding with the most practical weight**, and it is about a *translator*, not an engine: a
permissive translator accepts malformed measure logic at authoring time and defers the problem to a
runtime that may produce a plausible-looking wrong number. It is directly relevant to the Studio's CQL
editor, which reports translator diagnostics to an author as the compile gate.

### F3 — The `Long` type is broken at runtime, and it is a silent wrong ANSWER

Confirmed independently, and the most serious item here:

```
  1L + 2L                     → 12       (expected 3L)
  Sum({6L, 2L, 3L, 4L, 5L})   → 62345    (expected 20L)
  Abs(-1L)                    → 1        (expected 1L)
  minimum Long / maximum Long → runtime error
```

`1L + 2L` yielding `12` is **string concatenation instead of addition**. It does not throw and it does not
warn — it returns a number-shaped value that is wrong. Any measure arithmetic on `Long` would be silently
incorrect. **No WorkWell measure uses `Long`**, and this is a further reason not to start.

### F4 — Decimal precision is not applied to aggregate results

`PopulationStdDev({1.0,…,5.0})` → `1.4142135623730951`, expected `1.41421356`. The corpus declares
`decimal-precision-and-scale = 28,8`; results come back at full IEEE-754 width. Same for `StdDev`. A
cosmetic-looking difference that would matter to any measure reporting a computed decimal.

### F5 — `Ceiling` does not saturate or null at the Integer boundary

`Ceiling(2147483647.2)` → `2147483648`, expected `null`. The engine returns a value outside the Integer
range rather than the specified null.

## 5. Two harness defects found before publishing, recorded because they nearly became the headline

**The first full run reported 183 translation errors.** Both causes were ours:

1. **155 were `No default UCUM service available`.** `LibraryManager` takes a UCUM service as its fourth
   argument and defaults to one that throws, so every expression containing a quantity literal (`1.0'cm'`)
   failed to translate. Fixed by supplying a real validator (`scripts/cql-tests/ucum.ts`); probing showed
   the translator calls `validateUnit` only, and conversion happens at runtime inside `cql-execution`.
2. **16 were our own grading line.** `define Passed: Actual ~ Expected` will not type-check when a case's
   expected value has a different static type from its actual (`Equivalent(System.Integer,
   interval<System.Integer>)`) or when both are `Any` (reported as ambiguous). A fallback now retries
   without the comparison and grades the two values in JS, flagged as `gradedInJs` in the results.

**Publishing 183 as "the JS translator delta" would have been wrong by a factor of 15.** The real figure is
12. Recorded here rather than quietly fixed, because "the harness was the defect" is the outcome a
conformance exercise most needs to be honest about — and the fallback in (2) currently fires on **zero**
cases, so the results rest entirely on CQL's own equivalence.

## 6. A production gap this uncovered, not fixed here

**The runtime CQL translator cannot compile any CQL containing a quantity literal.** `compileCql` builds a
`LibraryManager` with no UCUM service, so the ELM Explorer in the Studio (`routes/measures.ts`) fails on
`1.0'cm'` with `No default UCUM service available`. `compileCql` now accepts an optional `validateUnit`
and the harness passes one; **production still passes none**, deliberately — wiring it in is a real
behaviour change that belongs in its own PR with its own tests. Follow-up issue named in ADR-060.

## 7. Reproducing

```bash
cd backend-ts
pnpm cql-tests:fetch          # clone at the pin into .cql-tests/ (gitignored)
pnpm cql-tests                # full run, ~11s, writes .cql-tests-results/results.json
pnpm cql-tests --check        # compare against scripts/cql-tests/baseline.json; non-zero on regression
pnpm cql-tests --file Interval --group Contains   # narrow, for iterating
```

The runner **refuses to print a figure** unless it parsed all 16 files and all 1,835 cases, and unless
every case landed in exactly one bucket summing to the total.

## 8. Limits, stated

- **One toolchain, one corpus pin.** These numbers are `@cqframework/cql` 4.0.0-beta.1 + `cql-execution`
  3.3.2 at `727219f4`. Both move; the baseline is only reproducible at that pin.
- **Not the official runner.** The published results come from `cql-tests-runner` driving a FHIR `$cql`
  operation. We drive the same corpus through our own translator and engine directly. The output is
  written in the runner's JSON shape so a future comparison is a format match, but posting vendor results
  to `cql-tests-results` requires the `$cql` endpoint — phase 2, not built.
- **`invalid-accepted` is a translator judgement, not an engine one**, and 36 of 42 is a high proportion.
  It is worth confirming against the Java translator before it is quoted externally.
- **No claim of "conformance" is made or licensed by this.** It is a measured pass rate over a public
  suite, with the failures enumerated. `docs/STANDARDS_CONFORMANCE.md` governs what may be said.
