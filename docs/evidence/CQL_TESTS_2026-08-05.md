# CQL language conformance — `cqframework/cql-tests` through WorkWell's translator and engine

**Date:** 2026-08-05 · **Corpus pin:** `cqframework/cql-tests` @ `727219f4` (2026-08-03) · **1,835 cases /
16 files** · **Toolchain:** `@cqframework/cql` 4.0.0-beta.1 (JS translator) + `cql-execution` 3.3.2
· **Harness:** `backend-ts/scripts/cql-tests/`, `pnpm cql-tests` · Roadmap V7, issue #296, ADR-060.

## 1. Result

```
  pass                 1622
  fail                  155    engine computed the wrong value
  translation-error      12    our JS translator rejected valid CQL
  runtime-error           4
  invalid-refused        11    rejected an invalid expression (6 at translation, 5 at runtime)
  invalid-accepted       31    translated AND evaluated CQL the corpus says is INVALID
  skipped                 0    we claim every capability the corpus declares

  1835 of 1835 graded, and 16 of those compared in JS rather than by CQL `~`
```

**On the upstream rule this run is 1,633 / 1,835, not 1,622** — see §2. Both numbers are stated because
they answer different questions: 1,622 is what our own seven-bucket scheme counts as a pass; 1,633 is what
`cql-tests-runner` would count, since it folds a correctly-refused invalid case into `pass`.

**Nothing is skipped, deliberately.** Issue #296 proposed a SkipList over the known-weak clusters (`Long`,
`LowBoundary`/`HighBoundary`, decimal precision). Skipping those would have deleted the finding this
exercise exists to produce, and would have reported a better rate over a smaller denominator. Every case
is graded.

## 2. What this measures that the published figures do not

Our runtime, `cql-execution` 3.3.x, already has a public report card at `cql-tests-runner.quality.hl7.org`
— **1,533 pass / 81 fail / 113 skip / 4 error**. **That run used the Java translator.** We translate with
the JavaScript one, `@cqframework/cql` 4.0.0-beta.1, and that delta has not been published anywhere.

**The comparison is indicative, not like-for-like, and must be quoted that way.** Three reasons:

1. **A different, smaller corpus.** 1,533 + 81 + 113 + 4 = **1,731** cases; ours is 1,835. (That figure is
   derived from their published counts, not read off a manifest. Note `parse-tests.ts` also calls "~1,731"
   a miscount *by issue #296* — #296 was describing OUR corpus with a number that happens to match theirs.)
2. **They skipped 113 cases we grade.**
3. **They score `invalid` cases differently, and we do too now.** `cql-tests-runner` grades an
   `invalid="true"|"semantic"` case as `pass` when the request fails for **any** reason, and folds it into
   the same pass/fail columns. We hold `invalid` out in its own buckets. Our 11 refusals are upstream
   passes, so the upstream-comparable total is **1,633**.

What *is* directly comparable: **our 4 runtime errors and their 4 errors are the same four cases** —
`minimum Long`, `maximum Long`, `1 * 1L`, `Precision(1.58700)`. Stated as an observation about the four
case names, from the published results page; it is not offered as proof of equivalence.

## 4. Findings

### F1 — The JS translator does not implement `Slice` (10 of the 12 translation errors)

`Slice({1,2,3,4,5}, 1, 3)` and every other arity: `Could not resolve call to operator Slice with
signature (list<System.Integer>, System.Integer, System.Integer)`. The operator is in the CQL
specification and the corpus tests it; our translator has no overload for it. The remaining two are
`timezone from …` (`Timezone keyword is only valid in 1.3 or lower`) and `ToConcept(Code)`
(`Expected an expression of type 'List of System.Code'`).

**Impact on WorkWell: none today** — no measure we run uses `Slice`, `timezone from`, or `ToConcept` on a
single `Code`. Reported because it is exactly the unpublished JS-vs-Java delta.

### F2 — 31 of 42 `invalid` expressions are accepted — translated AND evaluated

**This finding was materially overstated in the first draft, and the correction is instructive** (review,
#398). It said "only 6 of 42 are refused", because the harness graded purely on whether the expression
TRANSLATED. That is not what the corpus means. `cql-tests-runner` grades an `invalid="true"|"semantic"`
case as a pass whenever the request fails for **any** reason — translation *or* evaluation:

```ts
if (invalid === 'true' || invalid === 'semantic') {
    result.testStatus = response.status === 200 ? 'fail' : 'pass';
}
```

So `invalid` cases are now EXECUTED when they translate. Measured: **11 of 42 are refused — 6 at
translation and 5 at runtime** (`BooleanMinValue`, `BooleanMaxValue`, `DateTimeWidth`, `TimeWidth`,
`SingletonFrom12`), leaving **31 accepted**. And the first draft's headline example was the worst possible
choice: `Ceiling(2147483648)` is one of only **2** `invalid="syntax"` cases, which upstream routes to
normal grading rather than this branch at all — so it was never evidence for this finding.

**What survives, and it still has the most practical weight of anything here:** 29 of the 40
`true`/`semantic` cases are accepted and evaluated — overflow (`Exp(1000)`), domain errors (`Ln(0)`),
`minimum Boolean`. This is about a *translator*, not an engine: a permissive translator accepts malformed
measure logic at authoring time and defers the problem to a runtime that may return a plausible-looking
wrong number. It bears directly on the Studio's CQL editor, which uses translator diagnostics as its
compile gate.

**Before quoting this externally**, confirm against the Java translator — 31 of 42 is a high proportion,
and a difference that large is as likely to indicate something about how we invoke the translator as
about the translator itself.

### F3 — The `Long` type is broken at runtime, and it is a silent wrong ANSWER

Confirmed independently, and the most serious item here:

```
  1L + 2L                     → 12       (expected 3L)
  Sum({6L, 2L, 3L, 4L, 5L})   → 62345    (expected 20L)
  Abs(-1L)                    → 1        (expected 1L)
  minimum Long / maximum Long → runtime error
```

`1L + 2L` yielding `12` is **string concatenation instead of addition**. It does not throw and it does not
warn — it returns a number-shaped value that is wrong. Any measure arithmetic on `Long` would be silently
incorrect. **No WorkWell measure uses `Long`**, and this is a further reason not to start.

### F4 — Decimal precision is not applied to aggregate results

`PopulationStdDev({1.0,…,5.0})` → `1.4142135623730951`, expected `1.41421356`. The corpus declares
`decimal-precision-and-scale = 28,8`; results come back at full IEEE-754 width. Same for `StdDev`. A
cosmetic-looking difference that would matter to any measure reporting a computed decimal.

### F5 — `Ceiling` does not saturate or null at the Integer boundary

`Ceiling(2147483647.2)` → `2147483648`, expected `null`. The engine returns a value outside the Integer
range rather than the specified null.

### F6 — 68 of the 155 failures are an unimplemented operator, not a wrong value

`LowBoundary`/`HighBoundary` and quantity `mod` return `null` against a non-null expected. The `fail`
bucket's label — "engine computed the wrong value" — is what a reader quotes, and for these it is the
wrong description: nothing was computed. Recorded rather than re-bucketed, because the distinction needs
per-operator judgement the runner cannot make.

Related, and the same class as a defect already on the record: F4's decimal-precision gap is the second
precision inconsistency in this codebase — `docs/STANDARDS_CONFORMANCE.md` records `measureScore` emitted
at full float width where `qrda3-export.ts` formats the same quantity `.toFixed(4)`. The pair is more
informative than either alone.

## 5. Four harness defects found before publishing, recorded because two nearly became the headline

**The first full run reported 183 translation errors.** Both causes were ours:

1. **155 were `No default UCUM service available`.** `LibraryManager` takes a UCUM service as its fourth
   argument and defaults to one that throws, so every expression containing a quantity literal (`1.0'cm'`)
   failed to translate. Fixed by supplying a real validator (`scripts/cql-tests/ucum.ts`); probing showed
   the translator calls `validateUnit` only, and conversion happens at runtime inside `cql-execution`.
2. **16 were our own grading line.** `define Passed: Actual ~ Expected` will not type-check when a case's
   expected value has a different static type from its actual (`Equivalent(System.Integer,
   interval<System.Integer>)`) or when both are `Any` (reported as ambiguous). A fallback now retries
   without the comparison and grades the two values in JS, flagged as `gradedInJs` in the results.

**Publishing 183 as "the JS translator delta" would have been wrong by a factor of 15.** The real figure is
12. Recorded here rather than quietly fixed, because "the harness was the defect" is the outcome a
conformance exercise most needs to be honest about.

**A third defect, found by review and worth the most as a lesson:** a first draft of this section said the
fallback in (2) "currently fires on **zero** cases, so the results rest entirely on CQL's own equivalence."
That was read off `results.json` — where `gradedInJs` was **never serialized**. Both the author and a
reviewer confirmed `0` from a key that did not exist. It is **16**: the uncertainty-interval cases in
`CqlDateTimeOperatorsTest` genuinely need it. The field is now serialized, printed in the run summary,
recorded in the baseline, and any increase is a regression — because a number describing how much of the
result rests on the weaker grading path must be recorded, not inferred from an absent field.

**A fourth:** the `invalid` bucket was not measuring what the corpus means by `invalid` — see F2.

## 6. A production gap this uncovered, not fixed here

**The runtime CQL translator cannot compile any CQL containing a quantity literal.** `compileCql` builds a
`LibraryManager` with no UCUM service, so the ELM Explorer in the Studio (`routes/measures.ts`) fails on
`1.0'cm'` with `No default UCUM service available`. `compileCql` now accepts an optional `validateUnit`
and the harness passes one; **production still passes none**, deliberately — wiring it in is a real
behaviour change that belongs in its own PR with its own tests. Follow-up issue named in ADR-060.

## 7. Reproducing

```bash
cd backend-ts
pnpm cql-tests:fetch          # clone at the pin into .cql-tests/ (gitignored)
pnpm cql-tests                # full run, ~11s, writes .cql-tests-results/results.json
pnpm cql-tests --check        # compare against scripts/cql-tests/baseline.json; non-zero on regression
pnpm cql-tests --file Interval --group Contains   # narrow, for iterating
```

The runner **refuses to print a figure** unless it parsed all 16 files and all 1,835 cases, and unless
every case landed in exactly one bucket summing to the total.

## 8. Limits, stated

- **One toolchain, one corpus pin.** These numbers are `@cqframework/cql` 4.0.0-beta.1 + `cql-execution`
  3.3.2 at `727219f4`. Both move; the baseline is only reproducible at that pin.
- **Not the official runner.** The published results come from `cql-tests-runner` driving a FHIR `$cql`
  operation. We drive the same corpus through our own translator and engine directly. The output is
  written in the runner's JSON shape so a future comparison is a format match, but posting vendor results
  to `cql-tests-results` requires the `$cql` endpoint — phase 2, not built.
- **`invalid-accepted` is a translator judgement, not an engine one**, and 31 of 42 is a high proportion —
  confirm against the Java translator before quoting it externally. The 2 `invalid="syntax"` cases are
  excluded from any upstream comparison: `cql-tests-runner` does not take the invalid branch for them and
  we cannot reproduce its else-branch grading, because those cases carry no `<output>`.
- **16 of the 1,835 cases are compared in JS rather than by CQL's `~`** — the fallback for when the
  comparison itself will not type-check. That is a weaker grading path and it is now reported in the
  summary and tracked in the baseline rather than asserted to be dormant.
- **No claim of "conformance" is made or licensed by this.** It is a measured pass rate over a public
  suite, with the failures enumerated. `docs/STANDARDS_CONFORMANCE.md` governs what may be said.
