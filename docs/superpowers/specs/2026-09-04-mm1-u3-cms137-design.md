## 3. Multi-group execution (PR 2) — ADR-074

Today `official-executor-adapter.ts` reads `detailedResults[0]` and the router refuses a non-proportion
scoring; `OFFICIAL_MEASURE_SEMANTICS[id]` is one `numeratorMeansCompliant`.

- **The two-row shape and ADR-071 (spec-review finding 8 — the one design conflict).** ADR-071 fixed
  the catalog id to the vendored manifest's id and rejected an alias layer because it would be applied
  on every read, filter, upsert and rerun. A second row `cms137_engagement` with no directory of its
  own looks like that alias. It is not, and ADR-074 records the distinction as a **narrow, manifest-
  declared exception**: the parent manifest's `groups[].catalogId` (§2) is the vendored, hash-pinned
  declaration of which catalog ids the artifact serves, so `cms137_engagement` is a persisted id
  everywhere — outcomes, cases, exports, MCP, URLs — and **no id is translated at any read, filter,
  upsert or rerun site**. Exactly three load-time sites learn the mapping, each named here so the PR is
  auditable: (1) `config/official-measure-ids.ts` (U1) lists, in addition to the directory names, every
  `groups[].catalogId` declared by the manifests in those directories (one JSON parse per vendored
  measure at module load — a change from U1's "no JSON parsing", accepted because the alternative is a
  second table that can drift from the manifest); (2) `loadOfficialArtifact(id)` resolves a group id to
  its parent directory through the same declaration; (3) `executor-router.ts`'s catalogId guard (`:233`)
  accepts a group id whose parent manifest declares it. The exception is limited to ids a vendored
  manifest declares; it does not generalize to hand-written aliases. The alternative — one `cms137` row
  with a worst-of outcome and two rates rendered from evidence — was rejected because it changes the
  one-outcome-per-patient-per-measure invariant every product surface, export and case relies on,
  and it shows a number CMS never reports.
- **Semantics become per group.** `OfficialMeasureSemantics` gains optional
  `groups?: Array<{ id: string; label: string; catalogId: string; numeratorMeansCompliant: boolean; rationale: string }>`.
  For cms137: `Group_1 → { label: "Initiation", catalogId: "cms137" }`, `Group_2 → { label: "Engagement",
  catalogId: "cms137_engagement" }`, both `numeratorMeansCompliant: true`. A single-group measure keeps
  the flat shape. **Router guards, each named (spec-review finding 2):** the catalogId guard (`:233`) as
  above; the scoring guard (`:241`) accepts a manifest whose top-level `scoring` is `proportion` *or*
  whose `groups[]` all declare `proportion`; the semantics guard (`:266-271`) accepts a `groups` array
  as the definition for each `groups[].catalogId` when the flat field is absent.
- **The executor evaluates the artifact once per subject and fans out one `MeasureOutcome` per group
  catalog id.** `evaluateBatch(measureId, subjects)` returns, for `measureId = "cms137"`, outcomes keyed
  by subject for group 1; a sibling call for `"cms137_engagement"` returns group 2. **The memo is new
  code (spec-review finding 1):** `@work-well/official-executor`'s `FqmSubjectResult` type is widened
  to carry `detailedResults[i].stratifierResults` (fqm-execution 1.8.5 computes them; the package never
  read the field) and the adapter gains a result memo `Map<"<artifactSha256>|<subjectId>|<evaluationDate>", FqmSubjectResult>`
  **co-located with `cacheFor` and sharing its lifetime** — per executor instance, which the router
  constructs per run, never per process — populated in `evaluateBatch` and consulted before each fqm
  call, so the artifact runs once per subject per run however many group rows are routed.
  `populationMembership()` (`packages/official-executor/src/index.ts:295-305`) gains a group index
  argument instead of its `detailedResults[0]` first-wins reduction. `evidence_json.official` gains
  `group: { id, label }` and `strata: [{ id, inStratum }]`; `populationResults` stays the group's own
  array so MeasureReport/QRDA readers (ADR-046) keep working per row.
- **Exports (spec-review finding 5):** `measure-report.ts` emits `group: [group]` (`:414-427`, `:461`)
  and `qrda3-export.ts` reads `groups[0]` (`:123-126`, `:175-178`). Both gain a loop over the artifact's
  `groups[]`: the summary report emits every group with its stratifier results when either row is
  exported; the individual report emits the subject's membership in every group; QRDA III emits one
  rate per group. Each group's ADR-046 evidence trio (canonical, notation, membership) is derived per
  group row from that row's `evidence.official`, and `improvementNotation` comes from the manifest's
  per-group value (§2). Tested against the artifact's declared group ids.

## 4. Catalog and surfaces (PR 3)

- `cms137v14` is **deprecated once** by the ADR-071 seed mechanism, whose `LEGACY_OFFICIAL_IDS` table
  (`measure-seed.ts:21-26`) is widened from `{ legacyId, catalogId }` to `{ legacyId, successors: string[] }`
  so one audit event names both successors (reason: superseded by `cms137` and `cms137_engagement`);
  two new rows `cms137` (Initiation & Engagement of SUD Treatment — Initiation)

  `MEASURE_IDENTITY` entries `{ cmsId: "CMS137", mipsQualityId: "305", improvementNotation: "increase" }`
  for both, with a `group` label shown next to the name.
- Runnable rule: both ids listed on the Maui profile; both must be named in
  `WORKWELL_OFFICIAL_MEASURES` (they are routed together; a test refuses one without the other).
- Display table (U1 §6) gains both rows: Initiation OVERDUE → "New substance use disorder episode without
  treatment initiation within 14 days"; Engagement OVERDUE → "Treatment initiated but not engaged within
  34 days of initiation"; MISSING_DATA → not in the initial population (no new episode Jan 1–Nov 14).
- Programs overview shows two rates; a case opens on the row that failed; the CDS card renders both rows'
  outcomes as two cards when both are actionable (ADR-067 unchanged: no `critical`, no `systemActions`).

## 5. Data

U2's corpus generates the SUD cohort (new episode between Jan 1 and Nov 14 for 13+; initiation 45 %,
engagement 35 % of initiators, long-acting medication variant 10 %); nothing new is generated here. The
48-patient test fixture gains four SUD patients (one per outcome cell) in the corpus's first 48, so the
Maui e2e and the flip gate see the measure.

## 6. Verification and flip (PR 4)

MADiE gate 458/458; the second-engine sweep over the 48 cases (MM-1c pattern); `pnpm flip-gate --measure
cms137` (reports both groups); then the workflow edit appending `cms137,cms137_engagement` to

## 7. Out of scope

Stratified rates on the overview (export-only in U3); supplemental data elements (B8, deferred);
QDM execution (locked decision 3); any change to CMS137's logic.

## 8. Risks

- The multi-group memoization must be run-scoped, not process-scoped (the same rule
  `official-executor-adapter.ts` states for terminology): a process-lifetime cache re-introduces stale
  results across runs.
- The MADiE case comparison per group is the piece most likely to surface a harness gap; it is in PR 1
  deliberately, before any product code.
